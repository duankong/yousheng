# Windows 开黑语音 · 首版设计草案

2026-11-23。已选 A 版频道侧栏、LiveKit Rust SDK 语音引擎和 Rust 大厅的 Tokio、Axum。桌面、语音服务端、存储和打包按下表建议整体定稿。跨家庭网络的中转方式待实测。

## 玩家要做的事

一群朋友在不同地方用 Windows 打游戏。每个人只装同一个软件。任意一人点「开启大厅」，他的电脑同时运行服务端和客户端。他把邀请链接发给朋友，朋友点击后直接进入这个大厅。参与者无需安装组网软件、注册中转账号、填写 IP 或配置路由器。

进大厅后，成员看见频道、各频道里的人以及谁在说话。点击频道即可和同队成员语音、收发文字。成员可以持续开麦、按音量自动开麦，或按住全局快捷键说话。切换到游戏窗口后快捷键仍生效。直播、屏幕分享和游戏内浮窗留到后续讨论。

## 大厅、频道和权限

| 身份 | 能做什么 |
| --- | --- |
| 成员 | 查看、加入、退出和创建频道，控制自己的麦克风、扬声器及每位队友在自己耳机里的音量。每次只在一个频道通话和收发文字，同房成员可以同时发言。 |
| 频道创建者（房主） | 在成员权限上只增加「删除自己创建的频道」。 |
| 大厅管理员 | 能删除本大厅内任意频道。首版建议由开启大厅的人担任。 |

服务端根据连接所属的玩家身份检查每一次删除请求。客户端昵称仅供显示。即使频道里还有人，房主或管理员确认删除后，成员也应回到大厅并停止收发原频道的声音和文字。频道变空、房主离开或临时断线都保留频道。已删除的频道在重连后也应保持删除状态。

**建议的保存方式**：在开服者的当前 Windows 用户目录里保存大厅身份、频道和创建者。每台玩家电脑保存自己的身份，下次在同一安装环境中回来仍能管理自己的频道。主机明确停止大厅、退出服务端或关机时，本次通话结束。同一台主机下次开服恢复原大厅；朋友另行开服拥有自己的大厅。最小化客户端可继续开服。

## 技术选型

| 部分 | 建议采用 | 分工 |
| --- | --- | --- |
| Windows 桌面 | Tauri 2、Vue 3、TypeScript、CSS、Vite | Vue 显示大厅、频道聊天、成员和声音设置。界面通过 Tauri 把操作交给 Rust，只接收显示所需的状态与音量读数。 |
| 语音客户端（已选） | LiveKit Rust SDK、WebRTC 音频处理、CPAL/WASAPI | 从麦克风采集 PCM，处理后交给 LiveKit 编码成 Opus。订阅每位队友的音轨，独立调节音量后在本机播放。 |
| 语音服务端 | 官方 LiveKit Server（Go），Windows 原生程序 | 随同一安装包分发，由桌面程序在开启大厅时启动单节点服务，按活动频道转发每个人的音轨。停止开服时一并退出。 |
| 大厅业务（已选） | Rust、Tokio、Axum，建议使用 WebSocket 交换频道操作、消息和状态 | 开服者的 Rust 程序负责频道目录、成员身份、权限、文字聊天和语音入场凭证。 |
| 本地数据 | SQLite（通过 rusqlite）；本次文字消息放在主机内存里 | SQLite 保存大厅、固定频道和创建者。每位玩家本机保存设备、快捷键和个人收听设置。 |
| 分发 | Windows 10/11 x64 的单个安装程序，建议用 Tauri 的 NSIS 打包 | 将桌面客户端和语音服务端放进同一个安装包，注册邀请链接。 |

项目主要维护 TypeScript 界面和 Rust 原生业务两部分。Go 来自随包分发的官方 LiveKit Server，按需启动并随应用管理版本。Vite 只在开发和构建界面时使用。原始音频留在客户端原生层，界面只接收发言状态和试音电平。主机上的媒体服务直接转发已压缩的音轨，省去服务端逐路解码和重新编码的计算。主机同时也是玩家，它仍要为自己采集、处理和播放声音。同频道同时发言和收听的人越多，主机的上行需求越高。[LiveKit 音轨转发机制](https://docs.livekit.io/reference/internals/livekit-sfu/)

一个固定频道对应一个稳定的频道 ID。有人加入时，大厅服务按这个 ID 签发只允许进对应语音房间的短期凭证。语音房间空置回收后，频道目录仍由主机保留。删除频道时，大厅服务校验创建者或管理员身份，同时终止该频道现有通话、清除当局聊天并阻止旧凭证重新进入已删除的房间；重建同名频道时生成新 ID。具体撤权机制需要在自托管服务端验证。[LiveKit 房间生命周期](https://docs.livekit.io/intro/basics/rooms-participants-tracks/rooms/)

## 业务模块与依赖方向

首版建议把自己的 Rust 代码组织在一个程序里，按业务划分模块。官方 LiveKit Server 随包独立运行。前端的 `ui/src/features/` 按功能组织视图，原生端的 `src-tauri/src/` 放下表中的模块。应用入口负责启动、装配依赖和协调跨模块操作。这些是开发时的目录约定。

| 业务模块 | 自己负责的状态与规则 | 对外提供的结果 |
| --- | --- | --- |
| 大厅与邀请 `lobby` | 主机启停、邀请、玩家身份、在线会话及大厅管理员身份 | 一个经过验证的玩家身份、所属大厅和在线状态。网络直连或中转的变化封装在接入一侧。 |
| 频道与成员 `channels` | 固定频道目录、创建者、每位玩家当前加入的频道，以及创建、进出、删除的规则 | 频道列表、成员关系、操作权限和已生效的频道变更。固定频道的 SQLite 读写放在此模块边界。 |
| 频道文字 `chat` | 按频道暂存本次开服的消息，负责投递、回看和清理 | 应用先让频道模块核对发件人及目标频道，再交给聊天模块。聊天使用已确认的成员范围。 |
| 语音与个人收听 `voice` | 接入 LiveKit、设备与音轨、三种发言方式，以及个人收听设置 | 接受已授权的频道 ID，建立或结束通话，向界面提供发言和设备状态。个人静音和音量保存在收听者一侧。 |

**依赖方向。** Vue、Tauri 和 Axum 负责接收操作，交给 Rust 应用处理。频道权限判断只依赖玩家身份和频道状态。SQLite 的表结构和 LiveKit 的房间对象留在各自适配代码中，业务模块之间传递玩家 ID、频道 ID 和操作结果。首版采用直接调用，只在实际需要替换或独立验证的边界抽取接口。

**以删除频道为例。** 开服者从本机点击删除与好友从网络发起删除，经过同一个 Rust 操作。频道模块统一判断权限，界面根据它返回的结果展示按钮。删除生效后，应用拒绝该频道的新消息和入场请求，并协调聊天清理记录、语音结束通话。若语音清理需要重试，仍使用原频道 ID，避免误伤后来创建的同名频道。

**验收边界。** 频道权限可以在没有界面、数据库或麦克风的条件下验证。更换邀请中转服务只涉及接入代码。修改开麦阈值只涉及语音及其设置界面。语音连接失败时，界面能分别显示玩家所在的频道和实际通话状态。

## 联机方式比较

| 考虑过的方式 | 对玩家的影响 | 结论 |
| --- | --- | --- |
| 地址直连 | 两台设备的网络彼此可达时很直接，家庭网络可能需要设置入站连接。 | 作为软件内部可以利用的一条路径。 |
| 外部组网工具 | 现成工具能处理复杂网络，但双方需要额外安装和配置。 | 用户选择了单软件邀请。 |
| 应用内邀请和自动中转 | 朋友只需点链接。程序尝试直连，在无法直连时通过第三方转发；这时体验取决于中转质量。 | 用户选择的体验，无需自行租用云服务器。 |

语音媒体由 LiveKit Server 转发。异地好友需要能访问主机上的大厅服务、连接 LiveKit 信令，并建立双向语音。双方地址可达时优先直连；受运营商内网限制时使用公网中转。直连和中转之间切换时，应保留每名玩家的身份和所在频道。[LiveKit 网络要求](https://docs.livekit.io/transport/self-hosting/ports-firewall/)

邀请包含大厅连接信息和入场凭证，仅授予普通成员身份。Windows 安装包注册邀请链接处理方式；软件已打开时由现有窗口接收邀请，未打开时由系统启动。邀请指向离线大厅时显示「大厅暂时离线」并提供重试。主机恢复后可再次使用同一邀请。首版建议不做全网大厅目录。对于会拦截自定义协议的聊天工具，使用普通 HTTPS 邀请入口唤起已安装的应用，保留系统要求的打开确认；网页只负责唤起，无需存放频道或接收语音。交付时记录哪些分享入口已验证。

首版已接入 iroh。大厅和 LiveKit 信令通过同一条对等连接的双向流传输，语音的 WebRTC 数据包经过该连接转发。自动化已在同机两个独立客户端之间验证直连和公网共享中转上的双向音频。仍需在不同家庭宽带实测通话延迟和重连表现。共享中转受服务容量和可用性约束。[iroh 官方托管说明](https://www.iroh.computer/services/hosting)

## 通话和界面

**已选方案 A「频道侧栏」。** 左侧常驻频道列表，中间显示当前频道文字聊天，右侧显示队员和发言状态。Windows 客户端拟使用系统 WebView2 显示简体中文界面，已有运行时直接复用，缺失时由同一个安装程序补齐。[Tauri 官方 Windows 安装说明](https://v2.tauri.app/distribute/windows-installer/)

主界面优先显示「开启大厅／加入邀请」、当前大厅、频道及成员。加入频道后，玩家能立即看清自己是否静音、当前的发言方式、谁正在发言。创建者只在自己的频道看到删除入口，管理员可在所有频道执行删除。

建议把声音设置入口放在麦克风旁。在声音设置中可以选择输入设备、调节麦克风输入音量，并在试音时查看实时电平。输入音量决定队友听到自己的声音有多响。「语音激活」模式另有触发阈值，电平条同时显示当前音量、阈值标记和开麦状态。玩家可以先保持安静，再用平时打游戏的音量说一句话，调到背景声低于标记、自己的说话声能越过标记。声音设置也提供扬声器或耳机选择、通话输出总音量、降噪、回声消除和按键绑定。

在频道成员列表点开队友的音量控制，可单独调低或放大对方的声音，也可选择「我不听此人」。建议取消静音时恢复原先设定的音量。这些操作只影响操作者自己的播放，其他成员仍按各自的设置收听该队友。所有成员都能使用。

文字聊天直接放在当前语音频道内。建议首版支持纯文本，每条消息显示发送者昵称和时间。玩家即使关闭麦克风也能打字。服务端按发件人当前所在频道投递消息，切换频道时，聊天对象与语音队友一同切换。

**频道聊天记录保存在本地。** 按目前对「本地」和「没了就没了」的理解，由开大厅的电脑在本次开服期间按频道暂存消息。只要大厅仍在运行，玩家切回频道或掉线重连后可以回看本次记录。删除频道时清除该频道的消息。大厅停止后，本次记录到期；同一台电脑重新开服时恢复原有频道，每个频道的聊天区从空白开始。

客户端采用 LiveKit Rust SDK 的原生音频和标准 WebRTC 降噪、回声消除。产品负责持续开麦、按阈值激活或按键说话的切换。语音激活时，输入电平达到阈值即开始送音，降回阈值以下后建议稍作延迟再收麦，以保留句中短暂停顿和尾音。按键模式由原生全局快捷键接收按下和松开事件。手动静音优先于三种模式。每位队友独立调整音量或静音，之后再调整通话总音量。需先验证 Windows 原生播放路径能独立调低和放大单个队友，并让回声消除获得与实际播放一致的参考声音。切换设备、网络短断或重进频道后应恢复正确的设备与发言方式。以键盘旁的轻声短句和外放双向插话试听，Mumble 仅用作对照。[LiveKit 原生音频](https://docs.rs/livekit/latest/livekit/platform_audio/struct.PlatformAudio.html) · [标准音频处理](https://docs.livekit.io/transport/media/noise-cancellation/)

## 首版如何验收

以下是建议的验收范围。桌面端面向 Windows 10/11 x64，邀请优先测 Windows 版微信和 QQ 的好友消息，并用系统浏览器作为对照。覆盖游戏窗口获得焦点、全屏、软件已关闭、软件已打开这几种状态。在默认用户权限下验证按键说话；如果某款游戏或聊天软件限制这个操作，记录具体版本和表现。公开 HTTPS 入口交付时须绑定实际可用的托管地址；本地演示页面不能作为异地点击邀请已完成的证据。

1. 两台位于不同家庭网络的 Windows 电脑仅安装本软件。从聊天消息点击邀请，分别验证应用已运行和未运行时都能进入正确大厅。验证至少一组直接连接和一组强制中转的连接，记录接入时间与连接结果。
2. 同一大厅里建立两个频道并同时说话，各队只听见自己频道。验证普通成员和房主无法删除别人的频道，房主和管理员可执行各自允许的删除操作，含频道正在使用和房主重连两种情况。
3. 主机停止后其他玩家收到大厅离线提示。在原主机重开后，原有频道及创建者仍在，已删除的频道不会复现。
4. 建议以五人同局（含主机）作为首轮质量验收规模。分别测直连和中转，安排一人开音箱、一人边敲键盘边报点、两人同时讲话，以及全屏游戏中按键后立即报点。记录丢失的首字、断音、回声，以及开关语音前后的游戏帧时间变化和音频端到端延迟。区分自动化验证和多人多机实测结果。
5. 两个频道各有成员时，在其中一个频道边通话边打字，验证只有同频道队友收到消息。发文字时通话持续；切换频道后文字和语音都到新频道，麦克风状态、开麦方式保持原设置。
6. 在同一输入设备上调节麦克风音量，验证队友听见的响度随之变化。打开语音激活，以背景声和轻声报点分别试音，检查触发标记与实际送音一致，报点首尾清楚。将阈值调高后，切换到持续开麦或按键说话应仍能传出轻声报点。三种模式下手动静音均应停止送音。
7. 三人同频道时，甲调高、调低、静音再恢复乙的音量。检查甲听到的乙依次变化，甲听到的丙以及丙听到的乙保持原音量。甲调扬声器总音量时，甲听到的两位队友一起变化，两位队友听到的甲保持原音量。
8. 在频道里发送一条消息，退出后重进，再断线重连，两次都能回看这条消息。停止大厅并在原电脑重新开启，验证原频道仍在，聊天区为空。删除有消息的频道后再建同名频道，聊天区同样为空。

五人是建议的首轮验收规模。建议在两条以上不同家庭宽带上各运行一轮直连和中转测试，每轮通话 20 分钟。重复 20 次按键后立刻说两个字，首字均能辨认；两人外放对话时能互相插话，无持续回声。端到端单向语音延迟的首轮建议目标为第 95 百分位不超过 250 毫秒，须用本地录音参考或经校准的时钟测量。这些数值是待确认的目标。

在同一台游戏电脑、相同游戏场景中，分别记录软件未运行、客户端空闲、开服后空闲、五人实况语音四种状态。记录整个应用（含 WebView2 子进程和服务端）的内存、CPU 使用率、主机上行带宽，以及游戏帧时间的第 99 百分位。直连与中转分别记录，以观察开服和多人同时说话时是否增加卡顿。
